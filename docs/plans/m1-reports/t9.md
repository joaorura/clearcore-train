## Filtro do CV (§4.6) com WeSpeaker
- Candidatos: 706 de 3.269 `client_id` com >= 20 clipes (145.559 clipes). Por cliente, no máximo 100 clipes avaliados
  (amostra determinística por hash do caminho): 39.575 embeddings, 0 ilegíveis, ~12 min na CPU (16 núcleos, 12 threads;
  ~55 clipes/s), em cache retomável em `data/embeddings/` (fora do git). **Nenhuma GPU usada**, logo nenhum `gpu_lock`.
- Dev de calibração: 40 clientes (os de menor hash entre os candidatos), disjuntos do teste e do treino. Limiar de EER do
  WeSpeaker nos pares do dev: EER 4,64% no cosseno **0,3618** (5.000 alvo + 5.000 não-alvo).
- Cada clipe é comparado ao centróide **dos demais** clipes do cliente (leave-one-out); sai se o cosseno < 0,3618.
  Cliente com < 20 clipes retidos, ou com < 50% dos avaliados retidos, é descartado inteiro.
- Resultado: 129 clipes descartados (0,33%); 703 de 706 clientes retidos; 39.390 clipes retidos (train 33.662, dev 2.251,
  test 3.477). **Teste: 60 clientes retidos** (>= 40). Percentis do cosseno LOO: p1 0,448, p5 0,578, mediana 0,795, de modo
  que o filtro literal da spec é brando: o limiar de EER entre **pares** é baixo para uma comparação clipe-centróide.
- O teste do CV (60) sai dos retidos fora do dev, também por hash. Manifest filtrado (`data/manifests/cv27-pt-filtered.jsonl`)
  e split ficam em `data/`; só os SHA-256 vão ao git (`manifests/files/cv27-pt-filtered.sha256`). Teste automatizado:
  nenhum token de 128 hex (formato do `client_id`) em nenhum arquivo versionado.

## Desvios e pontos para o orquestrador
1. **CPU, não GPU**, para os embeddings (ORT sem CUDA; evitar dependência pesada, como pedido).
2. **Rede extra, mínima**: `speaker-info.txt` (4 KB) lido do zip do VCTK por Range (mesma fonte da Tarefa 8), para
   `speaker_sex` do VCTK; fica em `data/raw/vctk-0.92/` (não versionado). O LibriSpeech usa o `SPEAKERS.TXT` já em disco.
3. **Teto de 100 clipes por cliente** no filtro (balanceia e limita a CPU; ~145 mil clipes custariam ~45 min). Parâmetro
   `MAX_CLIPS_PER_CLIENT` em `scripts/m1_t9.py`; o cache é incremental. O CV filtrado tem, portanto, 39,4 mil clipes, não 145 mil.
4. **Acréscimos à spec §4.6**: centróide leave-one-out, e descarte do cliente com < 50% dos clipes retidos. Dev do CV
   (40 clientes) e dev do VCTK (8) são escolhas minhas (a spec fixa só o teste).
5. `gates-v2.yaml` tem `version: 2` (marcador do arquivo; o resto idêntico ao v1).
6. A identidade física não é verificável: um `client_id` pode ser o mesmo falante que outro (spec §4.6) e um leitor do
   CML-TTS poderia coincidir com um do LibriSpeech; a disjunção é por chave de falante, não por pessoa.
7. Os 3 clientes descartados (de 706) e as 129 exclusões por clipe saem de uma comparação clipe-centróide com o limiar de EER
   entre pares; se o dono quiser um filtro mais duro, o limiar é o único botão (`threshold`).
